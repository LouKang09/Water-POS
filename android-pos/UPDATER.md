# Water POS — in-app updates

## What is included in v1.4.0

The **App Updates** menu checks `GET /api/pos/app-update` against the running app.
- Web releases: Water POS updates its service worker and reloads the latest Railway web application, without uninstalling the APK, clearing credentials or deleting IndexedDB.
- Android releases: only published **verified APKs** are offered. The Android app downloads in the background through Download Manager, checks SHA-256, package identity, version code, and the *installed app's* signing certificate, and opens Android's standard installer prompt. No silent installation is attempted.
- Before applying either kind of update, the app checks for pending offline sales and unfinished orders. Any pending sales block the update.
- A network error never removes pending local transactions.

## IMPORTANT: existing debug signing keys

As of v1.3.0, the Railway `android-pos/Dockerfile` builds using `gradle assembleDebug` inside a Docker image. Gradle's debug signing key is generated within the image, so **successive builds are not guaranteed to share a certificate**.

Android requires matching signing certificates to update an app *in place*. The v1.4.0 APK generated by this Dockerfile is a **bootstrap/dev build**, not an automatically installable update over every v1.3.0 device. Android may reject it for incompatible signatures. **Never uninstall an installed POS app while unsynced sales remain.** Uninstalling normally deletes app data, including local transactions.

A production APK must be signed repeatedly with the *same securely held keystore* before it may be published in the in-app update feed. Ideally use the original signing key that matches the installed app. If that key no longer exists, migrate devices only after confirming all local sales have synced and a verified data backup is available.

## Publishing a safe native update

1. Keep Android `applicationId` as `com.waterpos.mobile`, with a higher `versionCode`.
2. Sign the APK with the original device-compatible certificate, using a secure signing process (for example, private CI secrets). **Never commit an Android keystore or passwords to GitHub.**
3. Publish the signed APK over HTTPS at either `water-pos-apk-builder-production.up.railway.app` or `water-pos-web-production.up.railway.app`. Other domains require an explicit code review and allowlist change.
4. Calculate SHA-256 of the actual downloadable APK and set the following Railway environment variables on the Water POS web service:
   - `POS_ANDROID_UPDATE_URL` = approved HTTPS URL ending with `.apk`
   - `POS_ANDROID_UPDATE_SHA256` = 64-character SHA-256 hex digest
   - `POS_ANDROID_UPDATE_VERSION_CODE` = numeric Android versionCode (must exceed the installed version)
   - `POS_ANDROID_UPDATE_VERSION_NAME` = Android display version, e.g. `1.4.1`
5. Deploy the changed variables. The backend publishes native metadata **only when all four settings validate**; otherwise `native` stays null, so the app cannot download an unverified APK through the update button.
6. Test on a device with *no pending transactions*, verify the download/certificate checks, and approve installation in the Android system dialog.

The updater **never self-rotates signing certificates**. To migrate away from debug builds without matching signing credentials, use a deliberate, data-preserving device migration plan instead of pretending an incompatible APK is an in-place update.
